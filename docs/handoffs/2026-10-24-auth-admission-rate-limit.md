## 1. 인증 슬롯 독점: 재현 완료

`internal/relay/server.go`의 전역 인증 슬롯은 128개다.
첫 인증 프레임을 최대 5초 기다리는 동안 슬롯을 유지한다.
IP별 제한은 초당 200회, 순간 400회여서 한 IP가 전역 슬롯을 채울 수 있다.
`security-probes.ts`는 같은 IP의 미인증 연결 128개를 약 113ms에 열었다.
다음 신규 업그레이드는 429였고, 연결을 닫은 후 101로 회복했다.

전역 자원 상한은 유지하면서 IP별 독점을 막는 공유 지점을 조사한다.
신뢰 프록시의 `ClientIP`, 실패·취소·인증 성공 시 자원 반환도 확인한다.
같은 IP의 정상 SDK 200명 연결과 집중 재접속을 함께 고려한다.

## 2. 정상 전송 제한: 발생 확인, 원인 미확정

현재 `internal/relay/connection.go:221`의 연결별 제한은 총 40회/s, 상태 20회/s, 상태 순간 허용량 2건이다.
노드·방 바이트 제한도 같은 `rateRejected` 계측과 오류 코드 9를 사용한다.
SDK 상태 전송과 서버 상태 묶음의 간격은 각각 최소 50ms다.

- Go 100명·정원 2명·100바이트·20Hz·10초: 제한 오류 100건. 같은 조건의 15초 재시험은 0건.
- Go 200명·정원 8명·100바이트·20Hz·15초: 0건.
- Go 200명·정원 16명·100바이트·20Hz·15초: 169건.
- Go 200명·정원 16명·679바이트·10Hz·30초: 0건. 같은 조건의 60초 시험은 102건.
- 실제 SDK 200명·정원 16명·679바이트·20Hz·30초: 제한 오류 19건. 본 측정 구간에서 발생했다.
- 실제 SDK 10Hz·30초: 기능 검사 종료 코드 0, 제한 오류 0건. 서버 쓰기 오류는 1건 증가했다.

총량 제한기를 두 번 차감하는 버그는 발견하지 못했다.
서버 수신 편차·묶음 도착과 순간 허용량의 충돌은 가설이다. 아직 확정한 원인이 아니다.
먼저 어떤 제한기가 어떤 수신 시각에 거부했는지 좁은 계측으로 확인한다.
단순히 제한을 크게 풀거나 오류를 무시해서 통과시키지 않는다.
SDK 10Hz의 쓰기 오류도 재접속·종료 영향인지 실제 전달 장애인지 구분한다.

## 같은 조건의 재시험

기본 노드는 슬롯 200개, 방 상한 512개, 기본 바이트 예산을 유지한다.
공개 HTTPS 로그인·매칭·배정과 실제 `LobbyClient`·`RelayClient` WSS를 사용한다.
인증서를 검증한다. 테스트 CA만 명시적으로 신뢰한다.

기존 도구:

- `cmd/relay-load/main.go`: 실제 Go TLS 소켓. 관리 API로 방을 만들어 공개 로그인·매칭을 거치지 않는다.
- 증거 폴더의 `sdk-load.ts`: 공개 API, 실제 SDK 200명, 상태·이벤트·하트비트·추가 2명 차단·집중 재접속.
- `run-load.py --suite diagnose|normal|ten-hz`: Go 프로필과 CPU·RSS·계측·정리 검사.
- `run-sdk.py --hz 20|10`: SDK 실행과 서버 자원 표본.
- `security-probes.ts`: 인증·Origin·크기 제한·반복 전송·미인증 슬롯·XFF 검사.

실행기는 기존 증거 폴더에 출력을 쓰는 구조다. 재시험 폴더에서 복사·조정해 기존 JSON을 덮어쓰지 않는다.
중첩된 증거 폴더를 만들면 TS 상대 import와 Python의 root 계산도 함께 확인한다.
Go 도구는 예열 2초다. SDK 도구는 예열 3초, 본 측정 30초와 재접속 후 5초를 사용한다.
정상 부하 기준은 예상하지 않은 오류 0건, p95≤100ms, p99≤200ms, RSS≤512MiB다.
서버의 제한·큐 초과·쓰기 오류 증가와 방·연결·슬롯의 회수도 확인한다.
의도한 연결 종료의 쓰기 오류를 성공으로 숨기거나 실제 장애로 단정하지 않는다.

Go 검사:

```sh
GOCACHE="$PWD/.cache/go-build" GOMODCACHE="$PWD/.cache/go-mod" .tools/go/bin/go test -race -count=1 ./...
GOCACHE="$PWD/.cache/go-build" GOMODCACHE="$PWD/.cache/go-mod" .tools/go/bin/go vet ./...
```

이 두 검사는 이전 소스에서 통과했다. 수정한 소스에서는 다시 실행한다.
서버와 부하 도구도 현재 소스로 다시 빌드한다. 소스·바이너리 해시를 새 증거에 고정한다.
하위 조건이 실패하면 동시 접속 수를 올리지 않는다. 이전 500명·1,000명 부하는 실행하지 않았다.

## 환경과 제외할 범위

이전 실행 환경은 macOS arm64, 논리 CPU 10개, Go 1.26.10, Node v24.3.0이었다.
같은 호스트의 서버·발생기 자원 경쟁을 고려한다. 인터넷·Linux·프록시·Android 성능으로 일반화하지 않는다.
로컬 소켓은 샌드박스에서 차단됐고, 이전 실행은 로컬 테스트용 승격 권한을 사용했다.
그 권한은 자동 검토에서 허용됐다. 실제 거절은 없었다.

전용 파일은 `.cache/live-load-20261023/operator.token`과 `tls/{cert,key}.pem`에 있다.
토큰은 0600이다. 값과 개인 키를 로그나 문서에 넣지 않는다. 인증서는 유효 기간을 먼저 확인한다.
기존 서버 포트는 19443·19092, 비교 포트는 19445·19094였다.
확장용 준비 포트 19444·19093도 포함해 이전 서버 세 개는 모두 종료했다.
새 실행 전 포트와 프로세스를 확인하고, 본인이 띄운 서버만 종료한다.

방 송신 예산의 병목은 별도 비교로 확인했다.
16명·1,127바이트·18Hz에서 4MiB/s는 p99 122ms, 8MiB/s는 51ms였다.
이는 의도한 바이트 예산의 효과다. 이번 두 문제를 고치려고 제품의 바이트 예산을 올리지 않는다.
자발 퇴장의 자격 정보가 TTL까지 남는 경로는 소스 점검 결과다. 이번 우선 수정 범위와 분리한다.
