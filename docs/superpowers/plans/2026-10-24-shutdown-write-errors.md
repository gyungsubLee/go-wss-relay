# 종료 뒤 쓰기 오류 분석과 수정 계획

> **For agentic workers:** Use the existing debugging, TDD, and verification workflow. The user authorized commit, diagnosis, necessary fixes, and same-condition retests.

**Goal:** 종료 뒤 쓰기 오류의 원인을 계측하고 정상 종료와 실제 전달 장애를 구분한다.

**Architecture:** 기존 종료 경로와 오류 계측을 유지하며 전용 overlay로 사건 순서를 기록한다. 필요한 수정은 부하 도구와 서버의 공유 종료 지점에 적용한다.

**Tech Stack:** Go 1.26.10, 기존 coder/websocket, 실제 TLS 소켓, 기존 SDK와 Python 실행기.

**Spec:** 사용자의 2026-10-24 후속 요청과 `docs/evidence/v2/2026-10-24-auth-rate-retest/REPORT.md`.

## 제약

- 기존 수정은 `e78f6a3`에 먼저 커밋했다. 원본 측정 파일을 바꾸지 않는다.
- 139건의 개별 오류 문자열은 원본에 없다. 같은 조건의 새 계측과 과거 개별 사건을 구분한다.
- `WriteErrors`를 종료 구간이라는 이유로 제외하지 않는다. 실제 기한 초과를 계속 검출한다.
- 슬롯, 바이트 예산, 쓰기 기한, TLS 검증을 유지한다. 호스트 부하는 순차 실행한다.
- 새 증거는 `docs/evidence/v2/2026-10-24-shutdown-retest/`에 쓴다.

## 검토 항목

- 취소 시각과 소켓 종료 시각: 수신 종료·쓰기 기한·쓰기 실패를 같은 연결에서 대응한다.
- 정상 종료: 새 송신을 멈추고 진행 중 쓰기를 마친 뒤 `Leave`, `Left`, 정상 Close를 확인한다.
- 종료 실패: 응답 누락·기한 초과·강제 정리를 실패로 기록한다.
- 실제 장애: 기존 차단 소켓 회귀 검사가 쓰기 오류를 계속 검출해야 한다.
- 지표 경계: 정상 종료를 기다리는 시간이 본 측정 지연이나 수신 수에 섞이지 않아야 한다.

## 검증 결과

- 기존 수정 커밋: `e78f6a3`.
- 같은 Go 6개 조건: 전체 구간 오류 0건, 정상 종료 1,000개, 자원 회수 완료.
- SDK 20Hz: 통과. SDK 10Hz: 재접속 구간 쓰기 오류 5건으로 엄격한 무오류 기준 실패.
- SDK 추가 진단 1건은 정상 Close를 받은 이전 연결의 알림 쓰기 실패였다. 원래 5건의 개별 소급 분류는 불가능하다.
- 느린 수신자 20Hz: 본 측정 쓰기 오류 13건과 실패 판정을 유지했다. 정상 수신자 87명은 정상 종료했다.
- 전체 race·vet·빌드와 독립 검토를 마쳤다. SDK 실패를 계수에서 제외하지 않았다.
- 자세한 근거는 `docs/evidence/v2/2026-10-24-shutdown-retest/REPORT.md`에 있다.
