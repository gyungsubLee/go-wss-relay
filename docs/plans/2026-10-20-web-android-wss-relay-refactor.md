# 웹·Android 공용 WSS 중계 서버 리팩터링 계획

작성일: 2026-10-20

상태: 목표 설계. 2026-10-21 새 포크에서 단일 노드 v2 기반 구현을 시작했다.
현재 구현 범위와 검증 결과는 [README](../../README.md)를 따른다. 분산과 클라이언트 구현은 완료하지 않았다.

## 1. 목표와 책임

웹에서 개발한 게임과 해당 게임을 APK·AAB로 패키징한 Android 앱이 같은 TypeScript 연결 모듈과 WSS 프로토콜을 사용한다.
Go 서버는 인증, 로비, 매칭, 방 배정, 데이터 중계, 접속 복구를 담당한다.
클라이언트는 좌표 계산, 보간, 오브젝트 모션과 화면 표시를 담당한다.

서버는 발신자와 방 권한을 검사한다. 클라이언트가 보낸 좌표·점수의 정당성을 보장하지 않는다.
충돌·사망·공용 먹이·점수의 결정권은 게임 계약에서 지정한다.
공용 상태에 단일 결정권이 필요하면 지정 클라이언트가 발표한다. 초기에는 그 클라이언트의 영구 이탈 시 경기를 종료한다.
재접속 유예와 영구 이탈을 구분하며, 자동 호스트 이전은 후속 요구사항으로 취급한다.

Snake.io의 서버 선택, 입력 변경 검사, 전송 제한, 바이너리 메시지와 보간 구조를 참고한다.
원본 APK의 NWS 바이트 형식이나 라이브러리를 복제하지 않는다.
APK 정적 분석으로 운영 서버의 분산 알고리즘·수용 인원·실제 전송 주기를 확인하지는 못했다.

## 2. 최종 결정

| 항목 | 결정 |
|---|---|
| 기본 통신 | HTTPS 제어 API와 WSS 중계 |
| 서버 구성 | 같은 코드베이스에서 단일 실행과 분산 실행 지원 |
| 프로토콜 | 새 `relay.v2` Protobuf 계약, Go·TypeScript 생성 |
| 인증 | 플레이어 인증 후 방·참가자·노드에 묶인 단기 접속권 발급 |
| 방 소유 | 활성 방 인스턴스 하나는 중계 노드 하나만 소유 |
| 상태 전달 | 참가자별 독립 전체 상태, 최신 대기 상태로 교체 |
| 사건 전달 | 제한된 FIFO, 초과 시 연결 종료와 명시적 복구 오류 |
| 캐시 | 참가자별 마지막 발표 상태와 참가자 목록만 보관 |
| 복구 | 같은 방 인스턴스에서 참가자 식별 유지, 연결 세대 교체 |
| 초기 정원 | 기존 최대 16명을 유지하고 실제 게임 프로필로 검증 |
| 데이터 저장 | 진행 방·좌표는 노드 메모리에 보관 |
| 초기 확장 | 중앙 배정 프로세스 하나와 여러 중계 노드 |

UDP와 UDP용 Challenge·HMAC·주소 바인딩을 새 WSS 경로에서 제거한다.
기존 클라이언트와의 동시 호환을 구현하지 않고, 새 프로토콜로 명시적으로 전환한다.
Protobuf 생성 도구, HTTP 검증, 만료 검사, 로비의 동시성 규칙과 배포 도구는 새 계약에 맞게 활용한다.

## 3. 연결 흐름과 인증

1. 플레이어가 로그인 또는 게스트 인증으로 플레이어 토큰을 얻는다.
2. 로비 시작 또는 빠른 매칭으로 참가자 구성을 확정한다.
3. 배정기가 노드를 선택하고 해당 노드에 방과 참가자 자리를 예약한다.
4. 예약 성공 후 배정을 확정하고 WSS 주소와 접속권을 반환한다.
5. 클라이언트가 WSS를 열고 첫 `Connect` 메시지에 접속권을 제출한다.
6. 노드가 접속권을 검증·소비하고 `Welcome`을 반환한다.
7. 클라이언트가 자신의 전체 상태를 발표한 뒤 상태와 사건을 교환한다.

배정 응답에는 `roomId`, `roomInstanceId`, `participantId`, `nodeId`, `websocketUrl`, `protocolRevision`, 접속권과 만료를 담는다.
서버가 참가자 ID를 결정하며, 클라이언트가 임의 ID로 다른 참가자를 선택하지 못하게 한다.
접속권은 짧은 유효기간과 일회 사용 식별자를 갖는다. 초기 연결과 재접속 권한은 구분한다.
접속권 만료가 이미 인증한 연결의 게임 참여를 자동 종료시키지는 않는다.

브라우저와 WebView의 표준 WebSocket 생성자를 사용한다.
토큰은 URL에 넣지 않고 첫 인증 메시지에 넣는다. 인증 전 시간·크기·접속 수를 제한한다.
운영자 비밀키와 노드 간 자격 증명은 웹 코드와 APK에 포함하지 않는다.
노드 간 요청은 사설 경로와 인증된 제어 통신을 사용한다.

## 4. 프로토콜과 상태 계약

필드·자료형·번호·상한·오류·복구의 구현 기준은 [relay.v2 메시지 명세](../specs/2026-10-20-relay-v2-message-spec.md)를 따른다.
기존 v1 스키마와의 대응, HTTP 배정 응답, 전체 Protobuf 계약안도 이 명세에 포함한다.

| 메시지 | 역할 |
|---|---|
| `Connect` | 버전과 초기 접속권 또는 재접속 권한 제출 |
| `Welcome` | 참가자 식별, 연결 세대, 참가자 목록, 캐시, 서버 제한 전달 |
| `StateUpdate` | 상태 번호가 포함된 참가자별 독립 전체 상태 발표 |
| `StateBatch` | 수신자에게 전달할 여러 참가자의 최신 상태 묶음 |
| `Event`, `EventAccepted` | 게임 사건 전달과 서버 접수 확인 |
| `PeerJoined`, `PeerStatusChanged`, `PeerLeft` | 참가자와 연결 상태 변경 알림 |
| `Ping`, `Pong` | 응답 확인과 왕복 지연 측정 |
| `Resync`, `SyncSnapshot` | 일관된 경계의 전체 캐시 재조회 |
| `Leave`, `Left`, `Error` | 명시적 퇴장, 처리 확인, 실패 알림 |

중계 서버는 게임 본문을 바이트로 취급한다.
상태를 발표한 참가자 ID·연결 세대·서버 수신 시각은 서버가 부여한다.
클라이언트가 제공한 시각을 권한이나 만료 판정에 사용하지 않는다.
Protobuf의 `uint64`와 시각을 TypeScript에서 손실 없이 다루는 규칙을 생성 설정과 호환 검사에 고정한다.

`StateUpdate` 본문은 앞선 메시지 없이 해석할 수 있는 전체 상태여야 한다.
뱀 게임의 예시는 머리 좌표·방향·길이·부스트 상태다. 몸통 복구에 필요한 경로 정보도 게임이 제공한다.
서버가 같은 참가자의 대기 상태를 교체하므로, 기본 계약에 델타 상태를 허용하지 않는다.

방 상태는 방별로 동기화하고, 전역 목록 잠금은 등록·조회·배정에 한정한다.
네트워크 쓰기 중에는 방 잠금을 유지하지 않는다.

상태와 사건 사이의 원자적 적용이나 전체 순서는 보장하지 않는다.
사건은 독립적으로 해석할 수 있어야 하며, 필요한 객체 버전과 생명주기 식별자는 게임이 본문에 담는다.
살아 있는 WSS 연결에서는 사건을 조용히 버리지 않는다. 연결 단절을 넘는 사건 전달은 보장하지 않는다.
사건 접수 확인은 상대 클라이언트의 수신·적용 완료를 의미하지 않는다.
점수·보상처럼 복구가 필요한 결과는 게임의 현재 상태 또는 별도 결과 계약으로 표현한다.

## 5. 전송량과 송신 큐

### 5.1 기본 정책

- 클라이언트 렌더링 빈도와 네트워크 발표 빈도를 분리한다.
- 변경한 상태를 초당 최대 20회 발표하는 프로필부터 검증한다.
- 수신자별로 각 송신자의 최신 대기 상태 하나만 유지한다.
- 노드는 초기 50ms 간격으로 상태를 묶어 수신자에게 전달한다.
- 사건은 상태 묶음 주기와 별도로 전송하되 큐와 대기 시간을 제한한다.
- 사건 큐 또는 쓰기 대기 한도를 넘긴 연결은 종료한다. 다른 참가자의 전송을 막지 않는다.
- 주기적인 상태 재발표와 Heartbeat를 사용해 변경이 없는 참가자의 응답 여부도 구분한다.
- 상태·사건·접속 제어별 크기와 빈도, 방·노드별 총 바이트 예산을 각각 둔다.

50ms는 초기 실험값이다. 묶음 대기와 네트워크 지연을 함께 측정하고 조정한다.
묶음 전송은 쓰기 횟수와 중복 메타데이터를 줄인다. 필요한 좌표 본문의 총량을 자동으로 줄이지는 않는다.
이미 TCP에 기록한 오래된 메시지는 최신 상태 교체로 취소할 수 없다.

SDK는 `bufferedAmount`를 관찰해 송신이 밀리는 동안 오래된 상태를 더 쌓지 않는다.
상태는 최신 값으로 교체하고, 연결이 끊긴 동안의 게임 사건은 자동 재전송하지 않는다.
이벤트 재시도가 필요한 게임은 사건 ID와 중복 처리 규칙을 별도로 지정한다.

### 5.2 전송량 산정

전원이 같은 방의 다른 참가자 상태를 받으면 아래 식으로 본문 전달량을 계산한다.

```text
전체 초당 본문 전달량 = C × (n - 1) × f × S
C: 전체 동시 참가자 수
n: 방당 참가자 수
f: 참가자별 초당 상태 발표 횟수
S: 상태 본문의 평균 바이트 수
```

| 가정 | 초당 본문 전달량 | 비트 전송률 |
|---|---:|---:|
| 100명, 방당 10명, 20회/초, 100바이트 | 1.8MB/s | 14.4Mbps |
| 500명, 방당 10명, 20회/초, 100바이트 | 9MB/s | 72Mbps |
| 1,000명, 방당 10명, 20회/초, 100바이트 | 18MB/s | 144Mbps |

위 값은 십진 단위의 계산 예시다. 실제 성능 측정값이 아니다.
Protobuf·WebSocket·TLS·TCP 헤더, 재전송, 초기 상태 전송, 사건과 운영 트래픽은 포함하지 않았다.
서버 NIC와 프록시가 처리하는 수신량도 별도로 계산한다.

### 5.3 수용량과 과부하 대응

노드 배정은 접속자 수뿐 아니라 예약 자리, 전송 바이트, 큐 대기와 CPU·메모리 여유를 반영한다.
노드 수용량은 동일 환경에서 지연 목표를 만족한 측정값으로 정한다.
초기 입장 상한은 측정한 최대치의 70%를 출발점으로 검증한다. 이 비율도 운영 설정으로 관리한다.
예산이 부족한 노드는 기존 방을 유지하고 새 방 배정을 거부한다.
전체 노드가 부족하면 대기 또는 명시적 용량 오류를 반환한다.

기존 초당 480회 방 전달 제한과 3,840회 전역 전달 제한을 새 처리량으로 간주하지 않는다.
제한값은 WSS 묶음·바이트·발신자별 정책에 맞게 다시 설정한다.
큰 방은 정원 증가 전에 구독 대상 제한을 검토한다.
거리·시야를 서버가 판단하려면 좌표 본문을 해석해야 하므로, 이는 게임별 후속 기능이다.

## 6. 사용자 증가에 따른 서버 분산

```text
클라이언트 ── HTTPS ── 접속·로비·매칭·배정 프로세스
                         ├─ 방 A·B → 노드 1의 WSS 주소
                         ├─ 방 C·D → 노드 2의 WSS 주소
                         └─ 방 E·F → 노드 3의 WSS 주소

클라이언트 ── WSS ── 배정받은 중계 노드
                       └─ 같은 방의 참가자에게 전달
```

### 6.1 방 단위 배정

한 방의 참가자는 같은 노드로 연결한다.
노드별 호스트명 또는 방 소유자를 인식하는 경로로 연결 대상을 지정한다.
WSS 연결을 임의 노드로 라운드로빈 배정하지 않는다. IP 고정 배정만으로 방 소유권을 표현하지 않는다.
같은 방의 상태를 Redis나 다른 노드에 매번 재전파하지 않는다.

배정 프로세스가 방의 `roomInstanceId → nodeId` 관계를 관리한다.
노드 선택은 호환 프로토콜·지역 설정·건강 상태·수용 여유 순서로 후보를 좁힌다.
지역별 노드가 생기기 전에는 지역 선택 기능을 추가하지 않는다.

### 6.2 예약과 실패 처리

노드의 빈 자리를 먼저 예약하고, 성공한 예약에 대해서만 매칭과 접속권을 확정한다.
방 생성 요청에는 멱등 식별자를 넣어 응답 유실 뒤 재시도가 방을 중복 생성하지 않게 한다.
배정 결과가 불명확하면 같은 요청 식별자로 조회하거나 재시도한다.
만료·취소·실패한 예약은 해제하며, 예약 자리도 노드 수용량에 포함한다.

노드는 Heartbeat로 활성 방·접속·예약·전송량·큐 상태와 실행 인스턴스 ID를 보고한다.
노드 재시작 시 실행 인스턴스 ID가 바뀐다. 이전 방과 접속권을 새 방으로 오인하지 않게 한다.
배정기가 노드를 사용할 수 없다고 판단하면 신규 배정을 중단한다.
노드와의 통신이 불명확한 동안 같은 방을 다른 노드에서 자동 생성하지 않는다.
노드가 실제로 사라졌다면 진행 방은 종료하고 클라이언트에 재매칭을 안내한다.

### 6.3 최초 분산 운영의 범위

단일 코드베이스에 `standalone`, `coordinator`, `relay` 실행 역할을 둔다.
처음에는 같은 프로세스로 실행하고, 분산 단계에서 배정 프로세스 하나와 중계 노드 둘 이상으로 분리한다.
최초 분산 단계의 배정 프로세스는 단일 작성자다. 로비·대기열·배정 메타데이터를 메모리에서 관리한다.
배정 프로세스 재시작 시 로비·대기열은 소멸한다. 클라이언트는 다시 조회하고 필요하면 대기열에 재등록한다.
기존 노드의 WSS 연결은 유지한다. 활성 방·참가자·예약을 재조회해 배정 정보를 복원한 뒤 신규 배정을 재개한다.
복원하지 못한 노드는 신규 배정 후보에서 제외한다.
플레이어 인증 키는 노드 재시작마다 바뀌는 연결 권한과 분리한다.

배정 API의 다중화나 재시작 중 무중단 매칭이 필요해지면 공유 저장소의 원자적 예약·소유권 계약을 추가한다.
그 단계에서 Redis나 데이터베이스를 선택한다. 최초 분산에 메시지 버스·Kubernetes를 선행 도입하지 않는다.

### 6.4 증설과 축소

증설한 노드는 등록과 건강 확인 후 새 방부터 받는다.
축소할 노드는 `draining` 상태로 바꿔 신규 배정을 중단하고 진행 방이 끝날 때 종료한다.
방이 실행 중인 노드 사이의 실시간 이동은 구현하지 않는다.
전체 사용자는 방을 나눠 확장한다. 한 방의 과부하는 전송량·정원 정책으로 처리한다.

## 7. 재접속과 캐시의 한계

연결 상태는 `연결 중 → 인증 중 → 활성 → 재접속 중 → 종료`로 구분한다.
접속권 만료, Heartbeat 제한, 복귀 유예, 방 종료 시각을 별도로 관리한다.
재접속은 같은 방 인스턴스·같은 노드에서 처리한다. 서버 주소를 임의로 바꾸지 않는다.

| 항목 | 초기 설정안 |
|---|---:|
| 초기 접속권 유효기간 | 30초 |
| WSS 연결 후 인증 대기 | 5초 |
| Heartbeat 간격 | 15초 |
| 응답 없는 연결의 종료 기준 | 45초 |
| 단절 판정 후 복귀 유예 | 30초 |
| 매치 방 유효기간 | 기본 30분, 최대 2시간 |

위 값은 초기 검증 프로필이며 운영 설정으로 관리한다.
클라이언트는 복귀 유예가 끝나면 같은 방 복구를 기대하지 않고 재입장한다.
접속권을 소비한 직후 연결이 끊겨도, HTTPS에서 권한을 재확인해 같은 참가자의 접속권을 다시 받을 수 있게 한다.

재접속 권한을 확인한 노드는 연결 세대를 증가시키고 이전 연결을 원자적으로 무효화한다.
클라이언트는 참가자·연결 세대·상태 번호로 오래된 메시지를 제외한다.
연결 세대가 바뀌면 그 참가자의 이전 캐시와 대기 상태를 제거한다.
노드는 참가자 목록과 캐시를 전달하고, 복귀한 클라이언트는 자신의 전체 상태를 다시 발표한다.
초기 상태 조회와 이후 업데이트 사이의 공백은 방의 상태 버전 또는 직렬화한 등록 절차로 방지한다.

유예 기간의 캐시는 마지막 발표 시각과 연결 상태를 함께 표시한다.
클라이언트는 이를 최신 게임 상태로 오인하지 않는다.
유예가 끝나면 참가자·캐시를 제거하고 퇴장을 알린다.
영구 이탈한 참가자를 오래된 상태가 다시 생성하지 못하게 생명주기와 연결 세대를 검사한다.

캐시는 전체 월드 체크포인트가 아니다.
공용 상태와 결과는 지정한 게임 권한자가 다시 제공해야 한다.
그 권한자가 사라진 경우 초기 계약은 경기 종료다. 중계 서버가 임의로 판정을 이어가지 않는다.

## 8. 웹·Android 공용 SDK와 배포

TypeScript SDK는 접속·인증·인코딩·Heartbeat·재접속·캐시 적용·오래된 상태 제외를 담당한다.
보간과 모션은 SDK에서 강제하지 않고 게임 클라이언트가 담당한다.
SDK는 전체 상태 생성 콜백과 상태·사건·참가자 변경 수신 콜백을 제공한다.
재접속 시도는 상한이 있는 지연과 무작위 간격을 사용한다.

웹에서는 페이지 가시성·재표시를 처리한다. Android 패키지는 앱 중단·복귀 알림을 같은 연결 관리로 전달한다.
백그라운드 중 타이머와 소켓이 계속 동작한다고 가정하지 않는다.
Android 프로세스 종료는 일반 재접속과 다르며, 재실행 시 재인증·재입장이 필요할 수 있다.

브라우저와 Android에서 동일한 WSS 계약과 클라이언트 구현을 사용한다.
선택한 패키징 도구의 실제 Origin을 확인하고 허용 목록을 설정한다.
HTTP CORS의 사전 요청을 인증 전에 처리한다. WSS Origin 검사는 별도로 적용한다.
Caddy는 TLS를 종료하고 중계 노드로 프록시한다.
프록시의 신뢰 범위를 지정한 뒤 접속자 IP를 적용하며, 임의 전달 헤더를 신뢰하지 않는다.
인증 전 IP 제한과 인증 후 참가자·방·노드 제한을 분리한다.

| 3. SDK·복구 | 공용 TS SDK, 웹·Android 테스트 클라이언트 | 브라우저↔Android 교환, 단절·복귀·이중 접속·유예 만료 검사 |
| 4. 전송량 검증 | 부하 클라이언트, 계측·프로필·보고서 | 목표 지연에서 노드 수용량과 바이트 예산 확정 |
| 5. 노드 분산 | 배정 프로세스와 노드 둘, 예약·등록·drain | 방 단일 소유, 중복 예약 방지, 증설·노드 장애·배정기 재시작 검사 |

단일 노드 측정을 끝낸 뒤 분산을 완성한다.
방 배정 응답과 방 인스턴스 식별자는 첫 계약부터 분산 가능한 형태로 정의한다.

검증 프로필은 최소 아래 조건을 포함한다.

- 작은 상태를 보내는 참가자 100·500·1,000명의 단계별 부하. 각 단계는 이전 결과를 보고 실행한다.
- 방당 2·8·16명과 초당 10·20회 발표를 비교한다.
- 실제 뱀의 전체 상태 크기와 초기 상태 전송 크기를 측정한다.
- 느린 수신자·저속 장치·지연·손실·재접속 집중을 별도 실행한다.
- 화면 잠금·앱 복귀·Wi-Fi와 이동통신 전환을 Android 실기기에서 검사한다.
- 예약 응답 유실·노드 종료·배정기 재시작·drain 중 재접속을 검사한다.

서버 내부 대기 지연과 실제 기기의 종단 지연을 따로 측정한다.
내부 처리 지연 p95·p99, 큐의 가장 오래된 대기 시간, 전송량, CPU·RSS·GC, 연결 성공률과 복구 시간을 기록한다.
측정 전에 대상 장비·네트워크·허용 지연·예산을 프로필에 고정한다.
접속 수만으로 처리 용량을 주장하지 않는다.
SDK 인코딩·상태 교체·이전 연결 거부·입퇴장과 캐시 정리에는 작은 회귀 검사를 남긴다.
