# 웹·Android WSS 구현 실행 계획

목표는 원래 계획의 1~5단계를 모두 구현·검증하는 것이다. 현재 구현에 맞춰 완료 기준을 줄이지 않는다.

## 참조와 소유권

MinbWebLib의 viewport, ES2022·Chrome/WebView 101·Safari 16 기준, 웹/native 번들 분리와 앱 복귀 계약을 따른다.
전용 중계 서버와 연결 SDK는 이 저장소가 소유한다. 참조 라이브러리의 원본은 수정하지 않는다.
SDK는 게임 본문을 해석하지 않는다. 데모의 좌표·모션·게임 이벤트는 client/src/demo가 소유한다.
접속 주소는 실행 설정, 방 정원과 전송 한도는 서버 정책, 플레이어 상태는 메모리 세션이다.

## 실행 순서와 증거

1. TS 메시지를 실제 v2 스키마에서 생성한다. uint64는 bigint로 유지한다.
2. SDK의 인증·상태 병합·Heartbeat·유예 내 재접속·스냅샷·세대 검사를 구현한다.
3. MinbWebLib 화면 기반을 사용하는 브라우저 데모를 연결한다.
4. 인증·로비·FIFO 매칭과 v2 할당·접속권 재발급을 연결한다. 두 브라우저의 교환을 확인한다.
5. Go↔TS 바이너리 호환, 단절·이중 접속·유예 만료·앱 복귀를 검사한다.
6. 부하 도구·계측을 구현한다. 장비·지연 목표·바이트 예산을 고정하고 100→500→1000명 순서로 측정한다.
7. standalone/coordinator/relay 역할, 노드 등록·예약·멱등 배정·복원·드레이닝을 구현한다.
8. 실제 두 노드에서 방 단일 소유, 증설·장애·배정기 재시작을 검사한다.
9. PRD·TRD·배포 설정·진행표를 최종 구현과 맞추고 원래 단계별 완료 기준을 다시 감사한다.

## 완료 판정

자동 클라이언트 검사는 실제 브라우저 교환과 구분한다. 데스크톱은 Android 실기기 검증을 대신하지 않는다.
실행하지 못한 항목과 필요한 외부 조건은 증거 문서에 남기며, 해당 단계는 완료로 표시하지 않는다.
운영 비밀과 서명키는 클라이언트나 저장소에 포함하지 않는다. 저장소 변경은 기존 codex/wss-v2 브랜치에서 진행한다.
