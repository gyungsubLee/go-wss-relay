# 종료 뒤 쓰기 오류 분석 — 2026-10-24

Go 부하 도구의 읽기 취소와 강제 소켓 종료가 측정 뒤 쓰기 오류를 재현했다.
과거 139건에는 개별 오류 문자열이 없어 각 사건의 원인을 복원할 수 없다.
이번 계측은 같은 조건에서 재현한 종료 경로의 근거다.
같은 6개 조건은 전체 구간의 오류 0건과 정상 종료를 확인했다.
SDK 20Hz는 통과했다. 10Hz는 재접속 중 쓰기 오류 5건으로 전체 무오류 기준에 실패했다.

앞선 인증·전송 제한 수정은 `e78f6a3`에 먼저 커밋했다.
[`이전 보고서`](../2026-10-24-auth-rate-retest/REPORT.md)와 원본 측정 파일은 보존했다.

## 원인과 구분

기존 Go 도구는 본 측정 뒤 읽기·쓰기의 공통 context를 취소했다.
작업이 끝나면 `CloseNow`로 소켓을 닫았다. `Leave → Left → Close(1000)`은 수행하지 않았다.
사용 중인 `coder/websocket`은 읽기 context 취소에도 연결을 닫는다.
서버가 상태나 연결 변경을 전송하는 동안 클라이언트가 연결을 끊으면 쓰기가 실패할 수 있다.

6개 조건을 진단 로그와 함께 다시 실행했다. 측정 뒤 오류는 `144, 1, 9, 9, 14, 1`건이며 합계는 178건이다.
준비·예열과 본 측정의 제한·큐·쓰기 오류 증가량은 모두 0건이었다.
원시 계수 178건과 사건 로그 178건이 일치한다. 전체 구간의 무오류 기준에서는 6개 조건 모두 실패다.

178건 중 166건은 취소된 클라이언트 읽기와 대응한다.
나머지 12건은 느린 수신자의 `broken pipe`이며, 읽기 종료 로그가 없어 분류를 보류했다.
178건 모두 서버 자체의 쓰기 기한 초과를 기록하지 않았다.
따라서 분류 이름 `unclassified_or_real_deadline`을 실제 기한 초과 12건으로 해석하면 안 된다.
메시지 종류는 `PeerStatusChanged` 165건과 `StateBatch` 13건이다.

느린 수신자 조건의 추가 진단은 오류 40건을 기록했다.
서로 겹치지 않는 분류는 읽기 취소 27건과 `CloseNow` 13건이다.
후자 13명은 지정한 느린 수신자 전원과 일치한다. 모두 읽기 종료 로그가 없으며, 소켓 종료 호출이 쓰기 오류보다 앞선다.
그 13건은 `StateBatch` 12건과 `PeerStatusChanged` 1건이다. 서버 자체의 쓰기 기한 초과는 0건이다.
원본 로그에는 `read_sleep_cancel` 사건이 없다. 그런 로그를 근거로 사용하지 않았다.

이 결과는 강제 종료와 정상 프로토콜 종료를 구분한다.
과거 139건과 새 178건을 일대일로 대응하지 않는다. 계측 로그와 실행 순서 차이도 재현 횟수에 영향을 줄 수 있다.
근거는 [`기준 분류`](baseline-classification.json), [`추가 진단 분류`](forceclose-classification.json), [`근거 감사`](diagnostic-evidence-audit.json)에 있다.

## 정상 종료 경로의 수정

서버에서도 별도 오류를 확인했다. `Leave` 뒤 후속 프레임을 읽으면 대기 중인 `Left` 전송을 취소할 수 있었다.
서버는 `Leave`를 처리한 뒤 쓰기 경로가 응답과 정상 Close를 마칠 때까지 기다린다.
[`수정 전 검사`](server-leave-red.log)는 후속 프레임이 응답을 취소하는 실패를 기록했다.
[`수정 후 검사`](server-leave-green.log)는 `Leave` 회귀 검사와 차단 소켓 검사를 race 조건에서 각각 3회 통과했다.
최종 소스의 전체 race 검사와 vet도 통과했다. 원본 명령과 종료 코드는 `static-checks.json`에 있다.

Go 도구는 새 상태 전송을 멈춘 뒤 진행 중 쓰기를 마치고 `Leave`를 보낸다.
수신 경로는 연결별 요청 순서와 맞는 `Left`를 확인한 뒤 `Close(1000)`을 확인한다.
응답 누락·비정상 Close·쓰기 실패·시간 초과·강제 정리는 실패로 기록한다.
최종 판정은 연결 수만큼의 `leftAcknowledgements`와 `normalClosures`를 요구한다.
`shutdownFailures`와 `shutdownForcedClosures`는 각각 0건이어야 한다.

원시 `writeErrors`는 종료 구간에서도 계속 집계한다.
참가자 슬롯·바이트 예산·쓰기 기한·TLS 검증은 유지한다. 종료 대기 구간은 본 측정 지연과 구분한다.

## 같은 조건의 비교

아래 오류 수는 측정 뒤 쓰기 오류다. 최종 6개 조건은 준비부터 종료까지 쓰기 오류가 모두 0건이었다.
조건은 참가자·방 정원·발행 Hz·상태 바이트·측정 초·느린 읽기 ms 순서다. Go 예열은 2초다.

| 조건 | 기존 오류 | 계측 재현 오류 | 최종 오류 |
|---|---:|---:|---|
| 200명·16명·20Hz·100바이트·15초·0ms | 6 | 144 | 0 |
| 100명·16명·10Hz·100바이트·10초·0ms | 1 | 1 | 0 |
| 200명·16명·10Hz·679바이트·30초·0ms | 12 | 9 | 0 |
| 200명·16명·10Hz·1127바이트·30초·0ms | 106 | 9 | 0 |
| 100명·8명·10Hz·679바이트·15초·500ms | 12 | 14 | 0 |
| 200명·16명·10Hz·679바이트·60초·0ms | 2 | 1 | 0 |
| 합계 | 139 | 178 | 0 |

최종 무오류 판정은 준비·예열·본 측정·종료 전체를 검사한다.
지연·CPU·RSS 기준과 방·연결·예약 슬롯 회수 기준도 유지한다.
총 1,000개 연결의 `Left` 응답과 정상 Close를 확인했다. 종료 실패와 강제 종료는 각각 0건이다.
6개 조건의 지연 p99 최댓값은 51.125ms다.
근거는 [`최종 실행 요약`](shutdown-final-summary.json)에 있다.
[`기준 실행 요약`](shutdown-baseline-summary.json)은 본 측정이 끝난 뒤 발생한 오류도 실패로 보존한다.

## SDK 재접속의 별도 결과

실제 SDK는 200명·정원 16명·679바이트·예열 3초·본 측정 30초·재접속 뒤 5초 조건으로 실행했다.
두 실행 모두 이벤트 507개를 승인했고, 수신자에게 전달할 이벤트 7,293건을 모두 전달했다. 재접속 200명도 모두 복구했다.

| 조건 | 정상 측정 지연 p99 | 재접속 뒤 지연 p99 | 전체 쓰기 오류 | 엄격한 전체 구간 판정 |
|---|---:|---:|---:|---|
| 20Hz | 68.518ms | 93.199ms | 0 | 통과 |
| 10Hz | 80.306ms | 88.098ms | 5 | 실패 |

10Hz의 5건은 모두 `enter-reconnect → enter-afterReconnect` 구간에 있다. 다른 구간의 오류 증가량은 0건이다.
클라이언트 SDK의 기능 검사는 통과했지만, 서버의 전체 구간 무오류 기준은 통과하지 못했다.
근거는 [`20Hz 원본`](sdk-process-final-20hz.json), [`10Hz 원본`](sdk-process-final-10hz.json)에 있다.

SDK의 `reconnect()`는 기존 WebSocket에 `Close(1000, "reconnect")`를 요청하고 즉시 새 연결을 연다.
이는 Go 도구의 취소·`CloseNow`와 다른 종료 방식이다. 재접속에는 `Leave`를 쓰지 않는다. `Leave`는 재개 권한을 끝내기 때문이다.

같은 SDK 10Hz 조건을 서버 진단 overlay로 다시 실행해 오류 1건을 계측했다.
원시 계수 1건과 사건 로그 1건이 일치한다. 이전 세대 1의 연결은 이미 정상 Close 1000을 수신했다.
그 뒤 `PeerStatusChanged` 쓰기가 닫힌 연결에서 실패했다. 서버 쓰기 기한은 지나지 않았다.
새 세대의 복구와 이벤트 전달은 모두 완료했다. 이 사건은 닫힌 이전 연결의 전환 알림 실패로 분류했다.

원래 5건에는 개별 로그가 없다. 따라서 진단 1건을 그 5건의 개별 원인으로 소급하지 않는다.
실패한 5건과 진단 1건을 계수에서 제외하지 않았다. 두 엄격한 판정은 모두 실패로 남겼다.
SDK의 일반 재접속에서 원시 쓰기 오류 0건을 항상 보장한다는 근거는 없다.
근거는 [`재접속 사건 분류`](sdk-reconnect-classification.json)와 [`SDK 진단 원본`](sdk-process-diagnostic-10hz.json)에 있다.

## 실제 장애와 시계의 한계

이전 100명·정원 8명·20Hz·679바이트·20초·느린 읽기 500ms 조건은 본 측정 중 쓰기 기한 초과 13건으로 실패했다.
이번 같은 조건에서도 본 측정 중 쓰기 오류 13건을 검출했다. 측정 종료 시 정상 연결 87개가 남았다.
정상 수신자 87명은 `Left`와 정상 Close를 확인했다. 도구는 오류 26건과 종료 실패 13건을 보고하고 종료 코드 1을 반환했다.
이 실패는 실제 전달 장애로 보존했다. 방·연결·예약 슬롯은 모두 회수했다.
근거는 [`느린 수신자 재검사`](slow-negative-final-lifecycle.json)에 있다.
차단 소켓 회귀 검사는 수정 뒤에도 쓰기 실패 경로를 검출했다.

추가 40건 진단의 벽시계 간격은 3,617.815506초다. 이 간격은 준비부터 회수까지 포함한다.
Go 도구가 설정한 본 측정은 15초다. 바이트 증가량과 전송률로 역산한 측정 간격은 15.5482195초다.
Go 소스는 그 전송률의 분모를 단조 시계인 `time.Since`로 계산한다.
두 간격의 차이가 난 원인은 확인하지 못했다. 호스트 절전이나 시계 조정으로 단정하지 않는다.

추가 진단의 사건 순서와 계수 대응은 종료 원인의 근거로만 사용한다.
중단 없는 15초 부하나 성능의 근거로 사용하지 않는다. 성능 판정은 별도로 기록한 최종 실행을 사용한다.
최종 실행 도구는 프로세스별 Unix 시각과 단조 시계의 경과 시간을 함께 기록했다.
최종 Go 6개 실행에서 두 시계의 경과 시간 차이는 0.164ms 이하였다.

## 최종 검사 상태

- 전체 `go test -race -count=1 -p 1 ./...`: 통과.
- `go vet ./...`: 통과.
- Go 6개 조건의 전체 구간·정상 종료·자원 회수: 모두 통과.
- 실제 SDK 200명·정원 16명·679바이트: 20Hz 통과, 10Hz 전체 무오류 기준 실패.
- 20Hz 느린 수신자 조건: 본 측정 쓰기 오류 13건과 실패 판정을 유지했다.
- 서버와 부하 도구 빌드: 통과.
- 소스 69개·실행 파일·CA 해시: 측정 전후와 현재 값이 일치한다.
- 직접 시작한 서버 PID 3개와 포트 19443·19092: 모두 회수했다.

검사 집계는 [`최종 검증`](runtime-verification.json)에 있다. SDK 10Hz 실패를 포함하므로 전체 무오류 통과로 판정하지 않았다.
