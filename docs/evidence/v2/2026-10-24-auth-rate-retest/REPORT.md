# 인증 대기와 전송 제한 수정 결과 — 2026-10-24

인증 대기의 IP 독점을 막았고, 정상 상태가 묶여 도착할 때의 제한 오류를 수정했다.
기존 SDK 두 조건은 전체 실행에서 오류 0건으로 통과했다. 기존 Go 11개 조건도 본 측정 기준을 모두 통과했다.

추가한 20Hz 느린 수신 조건은 무오류 기준에 실패했다. 느린 수신자 13명만 쓰기 기한을 초과했으며, 이 실패를 그대로 보존했다.
Go 도구의 측정 종료 뒤 쓰기 오류 139건도 별도로 기록했다. 모든 실행의 쓰기 오류가 0건이라는 뜻은 아니다.

## 원인과 수정

기존 인증 제한은 IP별 요청 횟수만 셌다. 첫 인증 프레임을 기다리는 동안 한 IP가 전역 슬롯 128개를 모두 점유할 수 있었다.
서버는 기존 mutex로 IP별 인증 대기 수를 관리한다. IP별 상한은 64개이고, 전역 상한은 128개다.
인증 성공·실패·취소 경로는 같은 반환 함수를 사용한다. 인증한 연결은 IP별 대기 수에 포함하지 않는다.
기존 전역 접속 검사를 IP 처리보다 먼저 적용한다. 신뢰 프록시와 주소 정규화는 기존 `ClientIP`를 사용한다.

상태 제한기는 서버가 프레임을 읽은 시각에 토큰을 차감한다.
방 잠금을 기다리는 동안 50ms 간격으로 상태 6개를 보냈다. 대기 뒤 수신 간격이 3μs인 프레임에서도 상태 제한 오류가 났다.
그때 전체 메시지 토큰과 노드·방 바이트 토큰은 남아 있었다. [`rate-red.log`](rate-red.log)에 원본을 보존했다.
상태 속도는 20개/s로 유지하고 순간 허용량만 2개에서 6개로 바꿨다. 이는 양 끝을 포함한 250ms의 상태 6개를 받는 예산이다.
전체 40메시지/s와 모든 바이트 예산은 유지한다. 8개 연속 전송은 계속 제한한다.
6개 허용량은 반복되는 수신 편차나 250ms를 넘는 정지를 모두 보장하지 않는다.

수정 전 자연 부하인 SDK 20Hz·30초와 Go 10Hz·60초는 이번 진단에서 오류를 재현하지 못했다.
제어한 읽기 지연의 실패 경로는 확인했다. 과거 간헐 오류가 모두 같은 원인이었는지는 확정하지 못했다.

## 실제 SDK 재시험

제품 `LobbyClient`와 `RelayClient`를 Node에서 실행했다. 공개 HTTPS 로그인·매칭·배정 후 WSS에 연결했다.
각 조건은 200명, 방 정원 16명, 상태 679바이트, 예열 3초, 본 측정 30초와 재접속 후 5초를 사용했다.

- 20Hz: 상태 p95 75.29ms, p99 82.60ms. 전체 제한·큐·쓰기 오류는 각각 0건이다.
  200명 모두 재접속했다. 재접속 p99는 519.71ms이며 서버 RSS 표본 최댓값은 40.22MiB다.
- 10Hz: 상태 p95 68.66ms, p99 75.17ms. 전체 제한·큐·쓰기 오류는 각각 0건이다.
  200명 모두 재접속했다. 재접속 p99는 525.13ms이며 서버 RSS 표본 최댓값은 41.23MiB다.

두 조건 모두 이벤트 507건을 접수했고, 예상한 수신 7,293건이 모두 도착했다.
추가 참가자 2명은 배정을 받지 못했다. 기존 참가자 200명은 활성 상태를 유지했다.
재접속·퇴장 구간을 포함해 쓰기 오류가 0건이었다. 이전 SDK 10Hz의 쓰기 오류 1건은 이번 실행에서 재현하지 못했다.
[`sdk-process-final-20hz.json`](sdk-process-final-20hz.json)과 [`sdk-process-final-10hz.json`](sdk-process-final-10hz.json)에 구간별 계측을 보존했다.

## 쓰기 오류의 구분

추가한 100명·20Hz·20초·느린 읽기 500ms 조건에서는 측정 중 쓰기 오류 13건이 발생했다.
같은 조건의 진단 실행에서 `p-0, p-8, …, p-96`만 1초 `StateBatch` 쓰기 기한을 초과했다.
이 13명은 의도한 느린 수신자와 정확히 일치한다. 측정 중 연결은 100개에서 87개로 줄었다.
일반 수신자의 지연은 기준 안이었다. 느린 수신자를 지연 표본에서 제외하므로 100명 전체의 유지나 무오류 통과를 뜻하지 않는다.
진단 실행에서는 측정 뒤 `p-86`의 `PeerStatusChanged` 전송도 `broken pipe`로 실패했다. 이를 측정 중 오류 13건과 분리했다.
[`slow-diagnostic-interpretation.json`](slow-diagnostic-interpretation.json)과 [`server-slow-diagnostic.log`](server-slow-diagnostic.log)에 참가자별 근거가 있다.

최종 Go 실행 14회에서 측정 종료 뒤 쓰기 오류는 139건이었다. 본 측정 오류와 별도로 기록했다.
Go 도구는 본 측정 결과를 채집한 뒤 읽기·쓰기를 취소하고 소켓을 닫는다. 이때의 오류를 `postMeasurementMetricDelta`에 기록했다.
수정 전 진단에서도 Go 종료 뒤 `broken pipe`를 직접 기록했다. 최종 종료 오류 139건 각각의 오류 문자열은 계측하지 않았다.
실제 SDK의 정상 재접속·퇴장과 Go 도구의 강제 소켓 종료를 같은 조건으로 해석하지 않는다.

## 인증과 보안 경계

같은 IP의 미인증 연결 64개를 102.38ms에 열었다. 다음 연결과 위조 XFF 요청은 HTTP 429를 받았다.
대기 슬롯 하나를 반환한 뒤 인증 두 건이 연속 성공했다. 인증 성공이 대기 슬롯을 즉시 반환한다는 근거다.
미인증 연결을 닫은 뒤 신규 업그레이드는 HTTP 101로 회복했다.
다른 유효 IP의 인증, 전역 128개 상한, IPv4 매핑 주소와 신뢰 프록시는 실제 소켓 회귀 검사로 확인했다.
인증한 연결이 상태 92건을 보내자 67건을 제한했다. 상태의 순간 허용량을 바꾼 뒤에도 남용 제한이 작동했다.
토큰·Origin·프레임 형식·크기 경계도 검사했다. [`security-final.json`](security-final.json)에 각 응답을 보존했다.

각 검사 후 방·연결·예약 슬롯을 회수했다. 마지막 고루틴은 7개였으며, 직접 실행한 서버와 포트를 모두 종료했다.

## 확인하지 않은 범위

200명·20Hz·679바이트·60초는 앞선 추가 느린 수신 조건의 실패 때문에 실행하지 않았다.
500명·1,000명 확장 부하도 실행하지 않았다. 범위 변경은 [`plan-amendment.json`](plan-amendment.json)에 있다.
서버와 발생기는 같은 호스트의 별도 프로세스에서 실행했다. 부하 발생기는 한 번에 하나씩 실행했다. 인터넷·Linux·실제 프록시·Android 기기 성능은 측정하지 않았다.
지연은 이동 표본이고 CPU·RSS는 1초 간격 표본이다. CPU 값은 `ps %cpu`의 프로세스 생애 평균이다.
원본 바이트 수는 TLS·TCP·WebSocket 오버헤드를 제외한다. 원본 증거 폴더는 그대로 보존했다.

다음 행동은 이 변경과 실패 조건을 검토하는 것이다. 500명·1,000명 운용 판정은 이번 결과로 대신하지 않는다.
