실제 클라이언트 부하테스트 결과 — 2026-10-23 실행, 2026-10-24 정리

200명은 연결할 수 있다. 그러나 무오류 운용 기준은 통과하지 못했다.
실제 SDK의 20Hz 부하에서 제한 오류 19건을 확인했다.
Go 클라이언트의 10Hz·60초 부하에서도 제한 오류 102건이 발생했다.
한 IP가 미인증 연결 128개로 신규 연결을 차단하는 현상도 재현했다.
배포 전에는 정상 전송의 제한 오류와 인증 슬롯 독점을 먼저 해결해야 한다.

이번 작업은 검사와 결과 기록이다. 서버와 제품 SDK 코드는 수정하지 않았다.
500명·1,000명 확장 시험은 하위 단계 실패 때문에 실행하지 않았다.

100명·8명 방·679바이트·10Hz·15초 조건은 방마다 수신자 하나를 500ms 간격으로 읽게 했다.
그 조건에서는 정상 수신자의 지연과 오류 기준을 통과했다.
실제 소켓 쓰기 차단은 전체 race 검사에 포함한 기존 회귀 검사도 확인했다.

제한 오류의 발생은 확인했다. 어느 제한기가 거부했는지는 아직 확정하지 못했다.
`internal/relay/connection.go:223`의 상태 제한은 초당 20건, 순간 허용량은 2건이다.
수신 편차나 일시 정지 후 묶음 도착이 이 제한과 충돌할 가능성이 있다.
현재 계측은 참가자·노드·방의 제한 원인을 같은 `rateRejected`로 합친다.
서버 수신 시각과 거부 원인을 추가로 기록해야 원인을 확정할 수 있다.
총량 제한기를 두 번 차감하는 코드는 발견하지 못했다.

대역폭 병목 비교

16명·방 하나·1,127바이트·18Hz·15초 조건에서 방 송신 예산만 바꿨다.
18Hz는 상태 전송 상한 20Hz보다 낮다.
두 조건 모두 제한 오류·큐 초과·쓰기 오류는 0건이었다.

| 방 송신 예산 | 실제 Protobuf 송신 | p95 | p99 | 수신 상태 | 일반 지연 기준 |
|---|---:|---:|---:|---:|---|
| 4MiB/s | 4.194MB/s | 119.74ms | 122.13ms | 54,446건 | p95 미달 |
| 8MiB/s | 4.986MB/s | 48.90ms | 50.77ms | 65,028건 | 통과 |

기본 4MiB/s 예산에서는 실제 송신이 예산에 도달했고 지연이 증가했다.
8MiB/s 비교에서 지연과 전달량이 개선되어 방 송신 예산의 병목을 확인했다.
비교 검사의 `passed=true`는 측정·오류·정리 조건을 뜻한다.
기본 4MiB/s 조건이 일반 지연 기준까지 통과했다는 뜻은 아니다.
두 비교 JSON의 `latencyGateApplied=false`와 `latencyWithinNormalGate`를 함께 확인한다.

16명 방의 1,127바이트 상태를 20Hz로 모두 전달하면 본문만 약 5.41MB/s가 필요하다.
이는 기본 방 예산 4MiB/s를 넘는다. 전송 주기·정원·본문 크기에 맞춰 예산을 정해야 한다.
기본 노드 송신 예산은 64MiB/s다. 방 예산만 높이면 노드 예산이 다음 제약이 될 수 있다.
16명 방에서는 상태 하나가 나머지 15명에게 전달되므로 정원 증가가 송신량을 늘린다.

SDK에는 최소 50ms의 상태 전송 간격이 있다. 서버도 50ms마다 상태를 묶는다.
SDK의 약 95-98ms p99는 두 전송 대기 구간이 겹치는 구조와 일치한다.
이를 CPU 부족의 증거로 해석하지 않는다. 함수별 CPU 프로파일은 수집하지 않았다.

보안 검사와 위험

1. 미인증 연결이 인증 슬롯을 독점했다. 우선 조치가 필요하다.
   같은 IP에서 미인증 WSS 연결 128개를 약 113ms 안에 열었다.
   이후 신규 업그레이드는 HTTP 429를 받았다. 연결을 닫자 HTTP 101로 회복했다.
   `internal/relay/server.go:140`의 전역 슬롯은 첫 프레임을 기다리는 동안 유지된다.
   대기 시간은 `server.go:192`에서 최대 5초다.
   IP별 동시 인증 제한과 프록시 연결 제한을 검토해야 한다.

2. 반복 전송 위반을 차단하는 경계가 약하다.
   인증한 연결 하나가 약 1초 동안 상태 92건을 보냈다.
   서버는 71건을 제한했지만 연결은 열린 상태였다.
   이는 상태 전송 상한을 넘긴 연결을 계속 읽고 응답하는 동작을 확인한 결과다.
   노드의 8MiB/s 바이트 예산을 초과한 공격을 재현한 결과는 아니다.
   `internal/relay/connection.go:230`은 전체 메시지를 읽고, `:241`은 먼저 디코딩한다.
   제한에 걸려도 `:277`에서 오류를 보내고 다음 메시지를 읽는다.
   반복 위반 시 종료 정책과 수신 단계의 자원 제한을 검토한다.

3. 자발 퇴장 후 자격 정보가 원래 방 만료까지 남는 경로를 소스에서 확인했다.
   `internal/relay/connection.go:347`은 퇴장 상태를 바꾸지만 재접속권을 즉시 지우지 않는다.
   `internal/relay/rooms.go:198`은 전원 퇴장한 방을 제거한다.
   남은 재접속권은 방과 참가자를 참조한다. `rooms.go:208`의 전체 정리가 만료 때 제거한다.
   공개 배정의 방 만료는 30분이고, 관리 배정은 최대 2시간이다.
   반복 퇴장이 현재 방·참가자 수보다 많은 객체를 유지할 수 있다.
   영구 누수로 단정하지 않는다. 이번 실행에서 내부 맵 수를 직접 측정하지는 않았다.

다음 방어 동작은 실제 로컬 요청으로 확인했다.

- 플레이어 토큰 누락·위조와 관리 토큰 누락: HTTP 401.
- 허용하지 않은 Origin: HTTP와 WSS 모두 403.
- 공개 포트에서 관리 상태 접근: 404. 자격 정보를 넣은 쿼리: 400.
- 64KiB 초과 JSON: 413. 텍스트 프레임: 종료 코드 1003.
- 16KiB 초과 클라이언트 프레임: 종료 코드 1009.
- 일회 접속권 재사용: 오류 코드 4. 잘못된 게임 규약: 오류 코드 3.
- 신뢰하지 않는 `X-Forwarded-For`를 바꾸며 로그인 64건 요청: 40건 허용, 24건은 429.

중복 JSON 검사는 알려지지 않은 필드도 포함한다. HTTP 검사만으로 중복 키 방어를 독립 검증했다고 주장하지 않는다.
기존 `httpx` 회귀 검사는 중복 키를 별도로 확인하며 전체 race 검사에 포함했다.
인증 우회는 이번 검사에서 발견하지 못했다. 전체 침투 검사나 최신 취약점 DB 검사는 수행하지 않았다.
[`security.json`](security.json)과 [`security-probes.ts`](security-probes.ts)에 결과와 재현 코드를 보존했다.

검증 범위와 재현

`go test -race -count=1 ./...`와 `go vet ./...`는 종료 코드 0이었다.
최초 샌드박스 실행은 로컬 소켓 권한 때문에 실패했다. 권한을 적용한 재실행 결과로 판정했다.
[`go-race.log`](go-race.log)에 최초 실패를, [`go-race-unsandboxed.log`](go-race-unsandboxed.log)에 재실행을 남겼다.
전체 결과 판정은 [`verification.json`](verification.json)에 있다.

이번 계측에는 다음 한계가 있다.

- 상태 지연은 16건마다 한 건을 표본으로 사용한다. 이동 표본은 최대 65,536개다.
- Go 지연은 소켓 전송 직전부터 측정한다. SDK 지연은 게임의 `publishState` 호출 직전부터 측정한다.
- 큐·쓰기 p95와 p99는 서버 실행 전체의 버킷 상한이다. 본 측정 구간의 정확한 백분위가 아니다.
- Protobuf 바이트는 WebSocket·TLS·TCP 오버헤드를 제외한다.
- OS CPU는 `ps %cpu`의 프로세스 생애 평균 표본이다. 순간 최대 사용률을 뜻하지 않는다.
- OS RSS는 1초 간격 표본이므로 짧은 최대값을 놓칠 수 있다.
- 쓰기 계측은 송신 예산 대기 시간과 직렬화 시간을 제외한다.
- 느린 수신자의 읽기 지연만으로 커널 버퍼가 가득 찼다고 단정하지 않는다.
- SDK의 `reconnect()`는 정상 종료 후 다시 연결한다. 강제 TCP 손실이나 무선 패킷 손실 검사는 아니다.
- 같은 호스트의 발생기와 서버가 자원을 공유한다. 인터넷·Linux·리버스 프록시·실기기 성능은 확인하지 않았다.
- 500명과 1,000명은 실행하지 않았다. 과거 측정 파일을 이번 결과로 재사용하지 않았다.

재현 코드는 저장소 루트에서 실행한다. 서버·발생기는 `out/live-load-20261023/`의 현재 바이너리를 사용한다.
전용 토큰과 새 개발 인증서는 `.cache/live-load-20261023/`에 만든다. 자격 정보와 키는 증거 폴더에 넣지 않았다.
기본 서버는 앞서 적은 19443·19092 포트와 기본 슬롯 200개를 사용한다.
비교 서버는 같은 옵션에 `--traffic-config`로 `{"roomEgressBytesPerSecond":8388608}`만 추가한다.

```sh
python3 docs/evidence/v2/2026-10-23-live-load/run-load.py --suite diagnose
python3 docs/evidence/v2/2026-10-23-live-load/run-load.py --suite ten-hz
python3 docs/evidence/v2/2026-10-23-live-load/run-sdk.py --hz 20
python3 docs/evidence/v2/2026-10-23-live-load/run-sdk.py --hz 10
python3 docs/evidence/v2/2026-10-23-live-load/run-load.py --suite saturation --tag room4mib
python3 docs/evidence/v2/2026-10-23-live-load/run-load.py --suite saturation --tag room8mib --management http://127.0.0.1:19094 --server-port 19445
NODE_EXTRA_CA_CERTS="$PWD/.cache/live-load-20261023/tls/cert.pem" node --experimental-transform-types docs/evidence/v2/2026-10-23-live-load/security-probes.ts https://localhost:19443
```

보존한 JSON은 당시 실행 결과다. 이후 정리한 Python 실행기는 검사 조건을 더 엄격하게 적용한다.
SDK 실행기는 서버의 쓰기 오류 증가도 실패로 처리한다. 따라서 기존 10Hz 실행의 종료 코드 0과 구분해야 한다.
재측정은 기존 증거를 별도로 보존한 뒤 진행한다. 현재 실행기는 같은 파일 이름을 사용한다.
테스트 노드 세 개는 모두 SIGTERM으로 종료했다. 종료 전 자원 수와 포트 폐쇄는 [`cleanup.json`](cleanup.json)에 있다.

다음 작업은 인증 슬롯 독점 방지, 제한 오류의 원인 계측, 실제 수신 편차를 반영한 전송 정책 검증이다.
그 수정 후 같은 조건을 다시 측정하고, 통과한 경우에만 동시 접속 수를 높인다.
